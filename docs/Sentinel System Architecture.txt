1. Overview

Sentinel is an AI-assisted cybersecurity monitoring platform designed to collect system and network telemetry, identify potentially suspicious behavior, and provide explainable security findings.

The platform is designed around a modular architecture so that event collection, detection, analysis, storage, and presentation can evolve independently.

Sentinel's primary goal is not to automatically declare an event malicious. Instead, it combines deterministic detection logic with contextual analysis to help security teams understand what happened, why it may be suspicious, and what evidence supports the finding.

The initial system will focus on a controlled development environment and will prioritize correctness, observability, explainability, and secure engineering practices over attempting to detect every possible threat.
2. Goals

    Collect and normalize security-relevant system and network events.

    Detect suspicious behavior using deterministic detection rules.

    Correlate related events into meaningful security findings.

    Use AI to provide contextual explanations of detected findings.

    Provide evidence supporting each finding rather than relying solely on an AI-generated conclusion.

    Provide a web dashboard for monitoring findings and system activity.

    Maintain an auditable record of detections and analysis.

    Design the system with clear security boundaries and least-privilege principles.

    Provide automated tests for core detection and application logic.

    Document architectural and security decisions throughout development.

3. Non-Goals

    Sentinel is not intended to replace a production Security Information and Event Management (SIEM) platform during its initial development.

    Sentinel will not attempt to guarantee detection of every attack technique.

    AI will not be treated as the sole source of truth for security decisions.

    Sentinel will not automatically execute potentially harmful remediation actions.

    The initial version will not attempt to monitor arbitrary third-party infrastructure without explicit authorization.

    Performance and scalability beyond the requirements of the initial development environment are not primary goals for the first release.

4. System Architecture

Sentinel follows a modular, event-driven architecture. Security-relevant telemetry enters through an ingestion layer, is normalized into a common event format, processed by deterministic detection logic, and correlated into security findings. Findings can then be enriched and explained by the AI analysis layer before being persisted and presented through the web application.

The initial architecture is intentionally modular so individual components can be tested, replaced, or scaled independently.

Core Components

    Event Normalization
    Converts different event sources into a consistent internal schema.

    Detection Engine

5. Component Responsibilities
5.1 Event Ingestion

The Event Ingestion layer is responsible for receiving security-relevant telemetry from supported sources.

Responsibilities:

    Accept incoming events.

    Validate event structure and required fields.

    Reject malformed or unsupported events.

    Attach ingestion metadata.

    Assign a unique event identifier.

    Record ingestion timestamps.

    Prevent untrusted input from directly reaching downstream components.

The ingestion layer must treat all incoming telemetry as untrusted input.
5.2 Event Normalization

The normalization layer converts source-specific events into Sentinel's internal event schema.

Responsibilities:

    Map source fields to a common schema.

    Normalize timestamps and identifiers.

    Normalize event severity and categories.

    Preserve relevant source information.

    Handle missing or optional fields.

    Produce validation errors for events that cannot be normalized safely.

Normalization allows the detection engine to operate independently of individual event sources.
5.3 Detection Engine

The Detection Engine evaluates normalized events using deterministic detection rules and heuristics.

Responsibilities:

    Evaluate events against detection rules.

    Generate detection results.

    Assign severity and confidence metadata.

    Record the rules responsible for a detection.

    Preserve the evidence that triggered a rule.

    Produce reproducible results for identical inputs.

The Detection Engine should not depend on an AI model to determine whether a rule matched.
5.4 Event Correlation

The correlation layer combines related events into higher-level findings.

Responsibilities:

    Identify relationships between events.

    Group events belonging to the same investigation.

    Track temporal relationships.

    Reduce duplicate findings.

    Maintain references to the underlying evidence.

Correlation should preserve the original events rather than replacing them with a summarized representation.
5.5 Finding Store

The Finding Store provides persistent storage for Sentinel's security data.

The initial implementation will use PostgreSQL.

Responsibilities:

    Store normalized events.

    Store detection results.

    Store security findings.

    Store evidence relationships.

    Store AI analysis results.

    Maintain timestamps and audit information.

    Enforce database-level relationships and constraints where appropriate.

5.6 AI Analysis

The AI Analysis layer provides contextual analysis and explanations for findings generated by deterministic components.

Responsibilities:

    Summarize relevant evidence.

    Explain why a finding may be suspicious.

    Identify potentially relevant context.

    Produce structured analysis.

    Clearly distinguish observed evidence from model-generated interpretation.

AI output must not overwrite the original evidence or deterministic detection result.
5.7 REST API

The REST API will be implemented using FastAPI.

Responsibilities:

    Provide authenticated access to Sentinel functionality.

    Expose findings and investigation data.

    Validate API input.

    Enforce authorization.

    Return consistent error responses.

    Provide API documentation.

    Prevent direct access to internal implementation details.

5.8 Web Interface

The web interface will be implemented using Next.js and TypeScript.

Responsibilities:

    Display security findings.

    Provide investigation workflows.

    Display supporting evidence.

    Display AI-generated explanations alongside their source findings.

    Provide filtering and search capabilities.

    Present system health and relevant operational information.

The frontend must not be treated as a security boundary. Authorization must be enforced by the backend.
5.9 Infrastructure

Docker will be used to provide reproducible development and deployment environments.

Responsibilities:

    Package Sentinel services consistently.

    Provide isolated development services.

    Define service dependencies.

    Simplify local environment setup.

    Support reproducible testing environments.

7. Security Boundaries

Security is a core architectural requirement of Sentinel. The system must assume that external telemetry, API requests, and other untrusted inputs may be malformed, manipulated, or intentionally malicious.
7.1 Trust Boundaries

Sentinel contains several trust boundaries:

    External Event Sources → Event Ingestion

    Client → REST API

    REST API → Application Services

    Application Services → PostgreSQL

    Application Services → AI Provider

    Docker Services → Host System

Data crossing a trust boundary must be validated and handled according to the trust level of its source.
7.2 External Event Sources

Events received from external sources must be treated as untrusted.

Controls:

    Validate event structure.

    Validate data types and field lengths.

    Reject malformed events.

    Apply reasonable payload-size limits.

    Sanitize data before displaying it in the frontend.

    Prevent untrusted event content from being interpreted as executable code.

7.3 API Security

The FastAPI service will act as the primary security boundary for client requests.

Controls:

    Authentication for protected endpoints.

    Authorization based on user permissions.

    Request validation using typed schemas.

    Rate limiting where appropriate.

    Consistent error handling.

    Avoid exposing internal implementation details in error responses.

    HTTPS in production environments.

The frontend must never be trusted to enforce authorization independently.
7.4 Database Security

PostgreSQL access must be restricted to trusted backend services.

Controls:

    Database credentials stored outside source code.

    Environment variables or a secrets-management mechanism for credentials.

    Least-privilege database accounts.

    Parameterized queries or ORM-generated queries.

    Database constraints for data integrity.

    No direct database access from the frontend.

7.5 Secrets Management

Secrets must never be committed to the repository.

Examples include:

    Database credentials.

    API keys.

    Authentication secrets.

    AI provider credentials.

    Deployment credentials.

Development environments should use environment variables or local secret files excluded by .gitignore.

Production environments should use an appropriate secrets-management solution.
7.6 AI Security

The AI layer is treated as an untrusted analytical component.

AI output must not automatically become a security decision.

Controls:

    Preserve original evidence separately from AI output.

    Clearly identify AI-generated content.

    Avoid sending unnecessary sensitive information to external AI providers.

    Validate structured AI responses.

    Handle model failures gracefully.

    Prevent AI output from directly triggering privileged actions.

7.7 Logging and Auditability

Security-relevant actions should produce appropriate audit records.

Important events may include:

    Authentication events.

    Authorization failures.

    Detection creation.

    Finding modification.

    Configuration changes.

    Administrative actions.

    System errors.

Logs must avoid unnecessarily storing sensitive information.
7.8 Dependency Security

Third-party dependencies introduce additional supply-chain risk.

The project should:

    Pin or constrain dependency versions where appropriate.

    Regularly review dependencies for known vulnerabilities.

    Remove unused dependencies.

    Keep production dependencies separate from development dependencies.

    Review dependency changes before merging.

7.9 Container Security

Docker containers should follow least-privilege principles.

Where practical:

    Avoid running services as root.

    Use minimal base images.

    Do not embed secrets in images.

    Limit unnecessary exposed ports.

    Keep containers isolated by function.

    Regularly update base images.

7.10 Security Principle

The overall architecture follows:

    Assume breach, minimize trust, validate at boundaries, preserve evidence, and minimize privileges.

8. Technology Stack

Sentinel uses a service-oriented technology stack selected to support security monitoring, typed APIs, persistent event storage, web-based investigation, automated testing, and reproducible development environments.
8.1 Backend — Python

Python is used for Sentinel's backend and security-analysis components.

Reasons:

    Strong ecosystem for cybersecurity, networking, data processing, and machine learning.

    Suitable for implementing detection and analysis pipelines.

    Large ecosystem of security-related libraries.

    Clear and maintainable syntax.

    Strong testing and type-checking support.

Python will primarily be responsible for:

    Event ingestion

    Event normalization

    Detection logic

    Correlation

    AI integration

    Backend services

8.2 API — FastAPI

FastAPI is used to expose Sentinel's backend functionality through a REST API.

Reasons:

    Native Python type-hint integration.

    Automatic OpenAPI documentation.

    Request and response validation.

    Good support for asynchronous workloads.

    Clear separation between API and application logic.

FastAPI will provide endpoints for:

    Authentication

    Events

    Detections

    Findings

    Investigations

    System health

    Administrative operations

8.3 Database — PostgreSQL

PostgreSQL is used as Sentinel's primary relational database.

Reasons:

    Strong data integrity guarantees.

    Mature transaction support.

    Relational modeling is appropriate for relationships between events, detections, findings, users, and evidence.

    JSON/JSONB support allows storage of source-specific event data.

    Strong indexing and querying capabilities.

PostgreSQL will store:

    Normalized events

    Detection results

    Findings

    Evidence relationships

    AI analysis

    Users and authorization data

    Audit records

8.4 Frontend — TypeScript + Next.js

The Sentinel web interface uses TypeScript and Next.js.

Reasons:

    Type safety across frontend code.

    Strong React ecosystem.

    Component-based UI architecture.

    Suitable for dashboards and investigation workflows.

The frontend will provide:

    Security dashboards

10. Detection Pipeline

The Detection Pipeline is responsible for evaluating normalized security events and identifying behavior that matches known suspicious patterns.

The pipeline is designed around deterministic, explainable detection before AI-assisted analysis.
10.1 Detection Philosophy

Sentinel will prioritize:

    Deterministic detection

    Reproducibility

    Evidence preservation

    Explainability

    Low false-positive rates

    Extensibility

A detection should be explainable without requiring an AI model.

10.3 Detection Rules

Each detection rule should have a stable identifier.

Example:
NET-001

AUTH-001

PROC-001

FILE-001

The identifier should remain stable even when the implementation of the rule changes.

Each rule should define:

     Rule ID

     Name

     Description

     Version

     Category

     Severity

     Confidence

     Conditions

     Required event fields

     Evidence fields

     References

     Enabled state

10.4 Rule Versioning

Detection rules must be versioned.

For example:
AUTH-001 v1

AUTH-001 v2

AUTH-001 v3

Historical detections should retain the rule version that generated them.

This prevents changes to detection logic from making historical results impossible to reproduce.
10.5 Severity

Sentinel will initially use:
INFO

LOW

MEDIUM

HIGH

CRITICAL

Severity represents the potential impact of the behavior detected.

Severity should not automatically determine whether an event is malicious.
10.6 Confidence

Confidence represents how strongly the available evidence supports a detection.

For example:
LOW

MEDIUM

HIGH

Confidence and severity are intentionally separate.

A detection may have:

     High severity + low confidence

     Low severity + high confidence

These represent different characteristics of a security event.
10.7 Evidence

Every detection should record the evidence responsible for the match.

Evidence may include:

     Matching event fields

     Source and destination information

     Process information

     User information

     Relevant timestamps

     Rule condition results

Evidence should allow an investigator to understand why the detection occurred without reading the detection implementation.
10.8 False Positives

False positives are expected in security detection systems.

Sentinel should track sufficient information to investigate false positives.

Potential future capabilities include:

     Dismissing a finding

     Recording a dismissal reason

     Marking a detection as expected behavior

     Rule tuning

     Suppression conditions

     Detection performance metrics

Detection tuning should be based on evidence rather than simply reducing the number of alerts.
10.9 Detection Testing

Every detection rule should have automated tests covering:

     Expected matches

     Expected non-matches

     Boundary conditions

     Missing fields

     Malformed input

     Severity assignment

     Evidence generation

Detection rules should not be considered complete until their behavior is covered by tests.
10.10 Initial Detection Categories

     Repeated failed authentication attempts

     Unusual authentication patterns

     Authentication from unexpected sources

Network

     Suspicious outbound connections

11. AI Analysis Pipeline

The AI Analysis Pipeline provides contextual analysis and explanations for security findings generated by Sentinel's deterministic detection and correlation systems.

AI is treated as an analysis and enrichment component rather than the authoritative source of security decisions.
11.1 AI's Role

The AI layer may:

    Summarize a security finding.

    Explain why the observed behavior may be suspicious.

    Identify relevant relationships between pieces of evidence.

    Provide contextual information.

    Suggest investigation questions.

    Help analysts understand complex findings.

The AI layer must not independently declare an event malicious without supporting evidence.

11.3 Evidence Selection

Sentinel should provide the AI model only with information relevant to the finding.

Potential context includes:

    Detection rule

    Detection rule version

    Detection reason

    Relevant events

    Event timestamps

    Source and destination information

    Process information

    User information

    Related findings

    Historical context where appropriate

Unrelated telemetry should not be unnecessarily included.
11.4 Context Construction

The backend is responsible for constructing the AI input.

The AI model must not have direct database access.

The application should explicitly select which information is provided to the model.

This creates a security boundary between Sentinel's data store and the AI provider.
11.5 Prompt Design

Prompts should clearly distinguish between:

    System instructions

    Security evidence

    User-provided information

    Previous AI analysis

Untrusted event content must be treated as data rather than instructions.

The system should be designed to reduce the risk of prompt injection through malicious telemetry.
11.6 Structured AI Output

AI responses should use a structured format where practical.

An analysis may contain:
{

  "summary": "...",

  "reasoning": "...",

  "observed_evidence": [],

  "potential_explanations": [],

  "investigation_questions": [],

  "confidence": "medium"

}

The exact schema will be finalized during implementation.
11.7 Output Validation

AI output must be validated before being stored or displayed.

Validation should check:

     Required fields

     Data types

     Maximum lengths

     Allowed enum values

     Malformed responses

     Unexpected content

Invalid AI responses should be rejected or marked as failed analysis rather than blindly persisted.
11.8 AI Failure Handling

The system must continue operating if the AI service is unavailable.

Possible failure states include:

     Provider unavailable

     Request timeout

     Rate limit

     Invalid model response

     Authentication failure

     Network failure

A failed AI analysis must not cause the underlying detection or finding to be lost.
11.9 AI Confidence

AI-generated confidence must remain separate from detection confidence.

For example:
Detection Confidence: HIGH

AI Analysis Confidence: MEDIUM

These represent different measurements and should never be treated as interchangeable.
11.10 AI Provider Abstraction

The application should avoid tightly coupling the detection system to a single AI provider.

An internal interface should allow the AI implementation to be replaced without modifying the detection engine.

11.11 Privacy

Only information necessary for analysis should be sent to an external AI provider.

Potentially sensitive information should be minimized, redacted, or anonymized where appropriate.

The system should document what information may leave the Sentinel deployment boundary.
11.12 AI Auditability

Every AI analysis should retain enough metadata to understand how it was generated.

Where appropriate, store:

     Provider

     Model

     Model version

     Analysis timestamp

     Finding identifier

     Analysis status

     Structured output

     Prompt version

Sensitive prompt content should be handled according to the project's data-retention and privacy requirements.
11.13 AI Security Principle

The core principle is:

    AI explains evidence; AI does not become the evidence.

Deterministic detections, original events, and supporting evidence remain authoritative security artifacts.

18. Architectural Decisions

This section records significant technical decisions made during Sentinel's development.

Each Architecture Decision Record (ADR) documents:

    The context surrounding the decision.

    The decision that was made.

    The reasoning behind the decision.

    The consequences of the decision.

    Conditions under which the decision may need to be revisited.

ADRs are intended to make Sentinel's architecture understandable and provide a historical record of why major technical decisions were made.
ADR-001 — Use Python for Backend and Detection
Status

Accepted
Context

Sentinel requires a backend capable of processing security telemetry, implementing deterministic detection logic, integrating with AI services, and supporting future security-analysis functionality.

The project also requires access to mature libraries for networking, data processing, validation, testing, and security-related development.
Decision

Python will be used for Sentinel's backend, event processing, detection engine, and AI integration.
Rationale

Python provides:

    A mature ecosystem for cybersecurity and security tooling.

    Strong support for data processing.

    Mature AI and machine-learning libraries.

    Type hints and static analysis capabilities.

    Extensive testing frameworks.

    Good developer productivity for security-analysis workloads.

Using one primary language for backend processing also reduces unnecessary complexity during the initial development phase.
Consequences
Positive

    Strong ecosystem for future security-analysis features.

    Rapid development of detection logic.

    Large selection of libraries.

    Consistent backend language.

Negative

    Python may not provide the same raw performance as lower-level languages for extremely high-throughput workloads.

    CPU-intensive workloads may eventually require optimization or dedicated worker implementations.

Revisit When

This decision should be reconsidered if profiling demonstrates that Python-based processing has become a significant performance bottleneck.
ADR-002 — Use FastAPI for the REST API
Status

Accepted
Context

Sentinel requires a typed REST API between the web interface and backend services.

The API needs request validation, clear endpoint definitions, authentication and authorization support, and automatically generated API documentation.
Decision

FastAPI will be used as Sentinel's primary REST API framework.
Rationale

FastAPI provides:

    Python type-hint integration.

    Request and response validation.

    OpenAPI documentation.

    Good asynchronous support.

    Clear API structure.

    Strong integration with Python application code.

Consequences
Positive

    Strong API validation.

    Automatically generated documentation.

    Consistent schema definitions.

    Good developer experience.

Negative

    The project becomes coupled to the Python web ecosystem.

    Additional architectural discipline is required to prevent API routes from containing excessive business logic.

Revisit When

This decision should be reconsidered if the API's performance, deployment requirements, or ecosystem needs significantly change.
ADR-003 — Use PostgreSQL as the Primary Data Store
Status

Accepted
Context

Sentinel must store events, detections, findings, evidence, AI analysis, users, and audit records while maintaining relationships between these entities.
Decision

PostgreSQL will be Sentinel's primary persistent database.
Rationale

PostgreSQL provides:

    Strong relational integrity.

    Transactions.

    Foreign keys.

    Constraints.

    Indexing.

    JSON/JSONB support.

    Mature tooling.

    Strong operational support.

The relational model is appropriate because Sentinel requires traceable relationships between security artifacts.
Consequences
Positive

    Strong consistency.

    Clear entity relationships.

    Mature query capabilities.

    Flexible support for structured and semi-structured data.

Negative

    Very large telemetry volumes may eventually require partitioning or additional storage systems.

    Database schema changes must be managed carefully.

Revisit When

This decision should be reconsidered if event volume or retention requirements exceed what the PostgreSQL-based architecture can efficiently support.
ADR-004 — Separate Detection from AI Analysis
Status

Accepted
Context

AI models can provide useful explanations and contextual analysis, but their output can be probabilistic, inconsistent, or influenced by untrusted input.

Security detections require reproducible and explainable behavior.
Decision

Deterministic detection will remain separate from AI analysis.

Detection rules will produce authoritative detection results, while AI will provide contextual analysis and explanations.
Rationale

This separation provides:

    Reproducibility.

    Testability.

    Clear evidence chains.

    Reduced dependence on model behavior.

    Easier debugging.

    Ability to replace AI providers independently.

Consequences
Positive

    Security decisions remain explainable.

    AI failures do not prevent deterministic detection.

    Detection rules can be tested independently.

    AI providers can be replaced.

Negative

    The architecture contains an additional processing stage.

    AI analysis may require additional infrastructure and cost.

Revisit When

The architecture may evolve as AI capabilities improve, but AI should not become authoritative without strong evidence and validation.
ADR-005 — Preserve Original Event Data
Status

Accepted
Context

Sentinel normalizes incoming telemetry into a common internal schema.

Normalization can remove source-specific information if the original event is discarded.
Decision

Sentinel will preserve the original event data alongside normalized fields where storage and privacy requirements permit.
Rationale

Preserving original data provides:

    Investigation capability.

    Evidence traceability.

    Debugging capability.

    Detection-rule development support.

    Ability to improve normalization without losing source information.

Consequences
Positive

    Better forensic context.

    Improved debugging.

    Greater auditability.

Negative

    Increased storage requirements.

    Additional privacy and retention considerations.

    Raw data may contain sensitive information and therefore requires appropriate handling.

Revisit When

Retention requirements, privacy constraints, or storage costs require a different raw-event strategy.
ADR-006 — Start with a Modular Architecture
Status

Accepted
Context

Sentinel contains multiple logical components, including ingestion, normalization, detection, correlation, API functionality, and AI analysis.

Deploying each component as an independent service from the beginning would introduce significant operational complexity.
Decision

Sentinel will initially use a modular architecture within a small number of deployable services rather than immediately adopting microservices.
Rationale

This approach provides:

    Clear internal boundaries.

    Lower operational complexity.

    Easier local development.

    Simpler debugging.

    Faster iteration.

Components can later be separated if measurable requirements justify doing so.
Consequences
Positive

    Easier development.

    Simpler deployment.

    Lower infrastructure overhead.

Negative

    Some components may eventually require extraction.

    Internal boundaries must be maintained carefully to prevent tight coupling.

Revisit When

A component requires independent scaling, deployment, fault isolation, or ownership that justifies separating it into an independent service.
ADR-007 — Use Docker for Reproducible Environments
Status

Accepted
Context

Sentinel contains multiple dependencies including PostgreSQL and backend/frontend services.

Development environments should be reproducible across machines.
Decision

Docker will be used to containerize Sentinel services, with Docker Compose initially used for local multi-service development.
Rationale

Docker provides:

    Reproducible environments.

    Service isolation.

    Consistent dependency versions.

    Easier onboarding.

    A path toward production container deployment.

Consequences
Positive

    Easier setup.

    Consistent development environments.

    Clear service boundaries.

Negative

    Additional container configuration.

    Docker introduces resource overhead.

    Developers must understand container networking and storage.

Revisit When

Deployment requirements justify a different infrastructure strategy.
ADR-008 — Treat AI Output as Non-Authoritative
Status

Accepted
Context

AI-generated analysis can contain incorrect assumptions, hallucinations, or interpretations influenced by malicious input.

Security decisions must remain grounded in observable evidence.
Decision

AI-generated content will never replace the original evidence or deterministic detection result.
Rationale

The authoritative security chain is:
Event → Detection → Evidence → Finding

AI analysis is an enrichment layer:
Finding → AI Analysis

This ensures that AI failures do not destroy or alter the underlying security evidence.
Consequences
Positive

     Better auditability.

     Reduced impact of AI errors.

     Easier provider replacement.

     Clear distinction between evidence and interpretation.

Negative

     Analysts must understand that AI analysis is advisory.

     The UI must clearly distinguish AI-generated content.

Revisit When

This principle should remain unless the system develops strong validation mechanisms capable of establishing trustworthy AI-assisted decisions.
ADR-009 — Version Detection Rules
Status

Accepted
Context

Detection rules may change as Sentinel evolves.

Changing a rule can change its behavior against the same event.
Decision

Detection rules will have explicit versions.

Historical detection results will retain the rule version that produced them.
Rationale

Versioning provides:

     Reproducibility.

     Historical accuracy.

     Easier debugging.

     Detection performance comparison.

     Safer rule updates.

Consequences
Positive

     Historical detections remain explainable.

     Rule changes can be tested independently.

Negative

     Additional metadata must be maintained.

     Old rule versions may need to remain available for historical analysis.

Revisit When

The rule lifecycle becomes sufficiently complex to require a more advanced rule registry or version-management system.
ADR-010 — Use Backend-Enforced Authorization
Status

Accepted
Context

The Sentinel frontend displays information and provides user interfaces, but frontend code can be modified or bypassed by a client.

Security authorization therefore cannot depend on frontend behavior.
Decision

All authoritative authorization decisions will be enforced by the backend.
Rationale

The backend is the trusted application boundary.

The frontend may hide unavailable functionality for usability, but this must never be considered a security control.
Consequences
Positive

     Stronger security boundary.

     Consistent authorization.

     Reduced risk from manipulated clients.

Negative

     Authorization logic must be implemented and tested on the backend.

     Frontend and backend permission states must remain synchronized.

Revisit When

The authorization architecture evolves to support more complex identity or policy-management systems.

19. Known Limitations

Sentinel is an evolving security engineering project. The initial architecture intentionally focuses on correctness, explainability, maintainability, and demonstrable security engineering practices rather than attempting to solve every cybersecurity problem.

The following limitations are known and accepted for the initial implementation.
19.1 Limited Telemetry Sources

The initial version will support a limited number of event sources.

It will not attempt to ingest every possible operating system, network device, cloud platform, or security product.

Additional integrations can be introduced as the ingestion architecture matures.
19.2 Limited Detection Coverage

Initial detection rules will cover a relatively small set of security behaviors.

This means Sentinel should not be considered a complete intrusion detection or security information and event management platform.

Detection coverage will expand incrementally.
19.3 Detection Accuracy

Deterministic detection rules may produce:

    False positives

    False negatives

    Incomplete context

Detection accuracy will depend on the quality and completeness of available telemetry.

Detection performance will be measured and improved over time.
19.4 AI Reliability

AI-generated analysis may contain:

    Incorrect interpretations

    Incomplete explanations

    Hallucinated context

    Inconsistent responses

AI output is therefore treated as advisory and does not replace authoritative security evidence.
19.5 AI Provider Dependency

The initial implementation may depend on an external AI provider.

This introduces potential:

    Availability limitations

    Rate limits

    Cost

    Network dependency

    Privacy considerations

The architecture attempts to reduce provider lock-in through an internal AI service abstraction.
19.6 Limited Distributed Processing

The initial implementation will process events using a relatively simple architecture.

A dedicated message queue and distributed worker system will not be introduced until event volume justifies the additional complexity.
19.7 Limited Multi-Tenancy

The initial system is not designed as a large-scale multi-tenant SaaS platform.

Tenant isolation, organization-level administration, and advanced resource quotas may require additional architectural work.
19.8 Limited Identity Management

The initial authentication system will provide the minimum functionality required for a secure development and demonstration environment.

Enterprise identity providers, SSO, advanced MFA, and complex identity federation may be introduced later.
19.9 Limited High Availability

The initial deployment is not designed to provide enterprise-grade high availability.

A production deployment requiring strong availability guarantees would require additional infrastructure such as:

    Redundant application instances

    Database failover

    Load balancing

    Health-based service recovery

    Backup and disaster recovery procedures

19.10 Limited Long-Term Data Retention

The initial implementation prioritizes functionality and traceability rather than large-scale long-term telemetry retention.

High-volume deployments may require:

    Partitioning

    Archival storage

    Compression

    Retention policies

    Lifecycle management

19.11 Limited Forensic Capabilities

Sentinel is initially designed for security monitoring and investigation rather than full digital forensics.

It will not initially provide capabilities such as:

    Disk forensics

    Memory forensics

    Malware reverse engineering

    Full packet capture analysis

    Advanced endpoint acquisition

19.12 Development-First Infrastructure

The initial infrastructure is optimized for reproducible development and demonstration.

Production deployments will require additional hardening, monitoring, backup, disaster recovery, secret management, and infrastructure controls.
19.13 Scope Principle

These limitations are intentional.

Sentinel will prioritize implementing a smaller number of capabilities correctly rather than claiming support for security functionality that has not been thoroughly implemented and tested.
